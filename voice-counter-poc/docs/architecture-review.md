# アーキテクチャレビュー（実装前）

実装に着手する前に、依頼者の当初案をテックリードの立場でレビューした記録です。
レイテンシの数値は公開情報と経験則に基づく**推定**で、実測値ではありません。実測はアプリの計測表示で行います。

## 1. 当初の要件と構成案

- 目的: 役所の手続きなどの QA ナレッジをもとに、音声で答える対話デモ
- 目標レイテンシ: ユーザーの発話終了から AI の音声返答開始まで **3 秒以内**（復唱を含めて自然なテンポ）
- 中核技術: 高速な型安全の意図判定モデル **Jev（TypeSafe AI）** によるルーティング
- 当初の構成案
  - クライアント: ブラウザ（React / Next.js）。STT は Web Speech API または低遅延なクラウド STT
  - バックエンド: Cloudflare Workers + Durable Objects（WebSocket とセッション管理）
  - 意図判定: Jev でトピックを判定（数十〜100ms 台）
  - 回答生成: カテゴリに紐づくナレッジを付与して、軽量 LLM（GPT-4o-mini 等）をストリーミング呼び出し
  - 音声合成: LLM の出力の最初の一文が確定した段階で順次 TTS に流す

## 2. レイテンシ予算（発話終了 → 音声再生開始）

| 区間 | 目安 | コメント |
|---|---|---|
| ① 発話終了の検出（VAD / endpointing） | 500〜1000ms | **見落とされがちな最大要因** |
| ② STT の確定 | 100〜800ms | ストリーミング型なら小さく、録音後にまとめて送るバッチ型は大きい |
| ③ Jev の意図判定 | 50〜150ms（+通信） | ボトルネックにはなりにくい |
| ④ LLM の最初のトークン | 300〜800ms | プロンプトが長いほど伸びる |
| ⑤ 最初の一文が確定するまで | 300〜700ms | 日本語は一文が長くなりがち |
| ⑥ TTS の最初のバイト | 200〜600ms | サービスによって差が大きい |
| ⑦ 通信・デコード・再生開始 | 100〜300ms | 日米間の往復が API 呼び出しごとに乗る |
| **合計** | **約 1.6〜4.3 秒** | 何もしないと 3 秒を超えうる |

### 改善策（効果が大きい順）

1. **Jev の判定直後に復唱を再生する**（例:「住民票の写しの取得についてですね。」）。③の直後に音が出るので、体感の待ち時間を大きく縮められる。→ 採用
2. **TTS に渡す単位を読点レベルまで細かくする**。最初のチャンクは短く、2 つ目以降は大きくする。→ 採用（`chunker.ts`）
3. **プロンプトと出力を短くする**。カテゴリでナレッジを絞り、「2〜3 文」と指示する。→ 採用
4. **endpointing を調整する**。無音 500〜700ms 程度。→ Hybrid VAD（600ms）として実験的に実装
5. **（任意）STT の途中結果（interim）で Jev を先行して呼ぶ**。→ 未実装（Phase 3 の候補）

### 設計上のリスク

- 複数ターンの文脈: 「それって何が必要？」は単体では分類できない → 直前の話題を Jev の `state` に含める
- 確信度が低い場合: 誤回答を避けるため聞き返す → 候補上位 2 つから聞き返す
- エコー: AI の声をマイクが拾う → `echoCancellation` の指定と、応答中は STT を止める半二重方式、ヘッドセットの推奨

## 3. Cloudflare Workers / Durable Objects の注意点

| 論点 | 注意点 | このプロトタイプでの対応 |
|---|---|---|
| CPU 時間 | 課金対象は CPU 時間で、`await fetch` の待ち時間は含まれない。ただし Free プランは 1 リクエストあたり 10ms と厳しい | **Workers Paid プラン前提**（README に記載） |
| WebSocket Hibernation | `acceptWebSocket()` を使うとアイドル中の課金を抑えられるが、休止するとメモリ上の状態が消える | 会話状態を **DO Storage** に保存 |
| ストリーミング中継 | `fetch` の `response.body` を読めば SSE を処理できる | 自前の SSE パーサ（`sse.ts`） |
| 音声の転送 | base64 だと 33% 膨らみ、CPU も使う | **バイナリフレーム**（8 バイトのヘッダ + PCM） |
| DO の配置場所 | 最初にアクセスされた地域の近くに作られ、移動しない | 未対応（必要なら `locationHint` を使う） |
| API キー | ブラウザに渡さない | secrets で管理し、STT には ephemeral token を使う |

公式: [Workers Limits](https://developers.cloudflare.com/workers/platform/limits/) / [DO WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)

## 4. 依頼者への質問と回答

| # | 質問 | 回答（要約） | 反映先 |
|---|---|---|---|
| 1 | 対象ブラウザは？ | Chrome だけで十分 | Chrome 前提（Web Speech API も Chrome のみ） |
| 2 | データの扱いは？ | PoC はダミーデータで行う | 架空の「サンプル市」のナレッジを作成 |
| 3 | 将来、電話につなぐ構想は？ | 将来はサーバー側 STT にしたいが、まずは最小コストで確認したい | ブラウザ側で処理する構成。サーバー側 STT は Phase 3 |
| 4 | STT は？ | Google の最新の AI STT を使いたい | `gemini-3.5-transcribe-live`（→ decisions.md ADR-001） |
| 5 | TTS / 音声の受け取りは？ | よくわからないが Google の AI を使う | Gemini TTS（→ ADR-002） |
| 7 | 割り込み（barge-in）は必要？ | まずは不要 | 半二重（→ ADR-007） |
| 8 | ナレッジの分量は？ | 市役所のホームページ程度と膨大。Jev で詳細に判別して関連文書を渡したい。PoC では簡単なダミーでよい | 12 トピックのダミー。スケールの方針は ADR-006 |
| 9 | 範囲外の質問は？ | 確認のうえ改めて連絡する旨を伝えるか、ウェブサイトへ誘導する | 定型文で案内（`OUT_OF_SCOPE_MESSAGE`） |

質問 6（TTS の比較）、10（複数ターン）、11（計測方法）、12（評価データセット）には明示的な回答がなかったため、Claude が判断しました。内容は decisions.md に記録しています。

## 5. 当初案からの変更点

| 当初案 | 採用した構成 | 理由 |
|---|---|---|
| STT: Web Speech API または OpenAI | Gemini Live `gemini-3.5-transcribe-live` | 依頼者の希望（Google の最新 STT） |
| LLM: GPT-4o-mini 等 | Gemini `gemini-3.5-flash-lite` | API キーを 1 つにまとめるため（ADR-003。差し替え可能） |
| TTS: OpenAI / ElevenLabs / ブラウザ | Gemini `gemini-3.8-flash-lite-tts` | 依頼者の希望と、キーを 1 つにまとめるため |
| フロント: React / Next.js | Vite + React | 依頼者の回答（シンプルに） |
| STT の経路: クライアント → WS → サーバー | ブラウザ → Google に直接接続 | 音声が Worker を経由しない分だけ遅延が減る（ADR-004） |
